# v0.5.4 engineering plan

Date: 2026-08-16  
Status: awaiting release approval
Release boundary: candidate source may be committed and pushed; tag, GitHub Release, npm publish
and the movable `v1` Action tag require a separate author approval.

## Objective

v0.5.4 corrects how the project describes and proves detector quality. The existing planted
fixtures verify that each built-in rule still follows its declared rule contract. They do not
measure production vulnerability precision or recall and must not be named or presented as
ground-truth accuracy evidence. A separate real-world regression corpus will turn already observed
failures into executable, reviewable gates without claiming statistical accuracy.

The release also removes an unnecessary version pin from the main-branch first-trial command,
opens a lower-friction support channel and submits the one currently eligible curated-list entry.

## Non-goals

- No new detector families, data-flow engine, MCP server or generic suppression engine.
- No production precision/recall percentage and no extrapolation from author-labelled fixtures.
- No broad refactor of source auditing, evidence schemas or release machinery.
- No automatic posting to promotional channels.
- No tag, GitHub Release, npm publication or `v1` movement without explicit approval.

## Evidence vocabulary

| Evidence set | Question answered | Allowed claim | Prohibited claim |
|---|---|---|---|
| Rule-contract conformance | Does each stable built-in rule still emit or stay quiet on its declared planted positive/negative neighbour, in the expected state? | All 22 declared planted contracts pass or fail reproducibly | Production precision, recall, exploitability or security coverage |
| Real-world regression corpus | Do previously observed correctness failures remain fixed under their minimal reproductions? | Named historical regressions are executable and currently pass | Representative prevalence, generic accuracy or third-party ground truth |
| Public-project case studies | What did a fixed-scope review observe and how were matches closed? | Project/commit-specific observations and closure evidence | A statistically representative benchmark |

## G2 - Real-world regression corpus

Implementation:

1. Add a structured case registry with an origin, observed failure, protected contract,
   executable check, expected result and remaining boundary for every case.
2. Reuse `docs/adoption/regressions.json` as provenance rather than copying historical descriptions
   into a second unlinked truth source.
3. Execute five narrow cases:
   - risk summaries render numeric state/severity counts and never `[object Object]`;
   - a package covered by `pnpm-workspace.yaml` inherits the root lockfile, while an out-of-scope
     package still reports the confirmed missing-lock condition;
   - nested JS/TS template literals retain complete source coverage;
   - one-to-one path-equivalent retest conditions remain unresolved/unchanged rather than creating
     a false fixed result;
   - numeric SVG assembled through `innerHTML` remains an expected benign match requiring manual
     closure, not a silently suppressed or falsely proven-safe result.
4. Generate versioned JSON and Markdown under `docs/regressions/` with a mandatory boundary:
   historical regression evidence is not a representative accuracy benchmark.

Focused gates:

- Every case executes product code or renderer code, not a duplicated reimplementation.
- Restoring each protected failure makes its case fail or an equivalent existing plant-the-failure
  test demonstrates the gate.
- Output contains no sensitive source contents and uses deterministic paths/values.
- The benign-match case records `expected_benign_match` and the required human closure instead of
  changing detector behavior.

Completion record (2026-08-16):

- Added one deterministic runner and generated JSON/Markdown for four minimized v0.5.2 failures

  renderers, JS/TS inspection or v3 baseline comparison. Historical descriptions and fix provenance
  are generated from `docs/adoption/regressions.json`.
- The numeric SVG case remains `suspected`, is manually classified `expected_benign_match`, requires

- Focused verification: 5 cases passed, 0 failed; validator mutations prove a failed guard and an
