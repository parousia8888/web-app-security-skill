`30402c866b86d78b66d0d4b495fee40ff6a6f160`

`63c28f3a55ed9dcf0a7485e6a02d535d8a9792af`

## 1. Objective

Review and remediate every mechanism raised by the 26-issue external audit without treating the
auditor's severity, causal explanation or proposed patch as authoritative by default. No issue is
dropped because one part of its argument is overstated. A disputed issue becomes a narrower test,
documentation or design obligation until the underlying observation is resolved.

This is a correctness and evidence-integrity milestone. It does not add a broad scanner catalogue,
active testing, automatic project modification or a production accuracy claim.

## 2. Evidence policy

The original external issue remains immutable input. Maintainer disposition is recorded separately:

- `accepted`: the reproduced mechanism and material impact are supported.
- `accepted_reframed`: the mechanism is supported; severity, affected boundary or causal wording is
  narrower than the external claim.
- `claim_corrected`: part of the explanation conflicts with source or dependency behavior; the
  underlying fixture, divergence or missing contract still receives a disposition.
- `verification_pending`: supplied execution evidence is credible but has not yet been independently
  rerun against the exact target and tool commits.

No issue may be closed with only `not reproducible`. Closure requires the exact baseline, command,
environment, observed output and an explanation of whether the difference is version drift,
platform behavior, fixture error, documentation ambiguity or a product defect.

Detector severity and audited-application vulnerability severity remain separate. A false-clean
coverage result can be a high-severity product correctness defect without proving that the missed
application route contains a critical vulnerability.

## 3. Version and scope boundary

The signed `v0.7.2` tag and the report's line-number baseline have different Git trees. The report
anchors all source citations to `63c28f3`, five commits after the release tag. Core analyzer files
relevant to the supplied findings did not change across that interval, but release-state, README and
public-distribution conclusions must be reproduced separately at both identities when relevant.

Every issue record must therefore contain:

1. tool source commit;
2. target or fixture commit/digest;
3. runtime and operating-system identity;
4. exact command and exit code;
5. sanitized observed output;
6. whether the check concerns release source, post-release public state or both.

## 4. Issue ledger and closure contracts

### EA-01 - persisted scope target and external lockfile containment

- Disposition: `accepted_reframed`; handle privately until the containment fix is public.
- Preserve: a persisted scope can supply a lockfile path outside the intended lexical project root
  and that value can reach the OSV adapter argument list.
- Correct boundary: scope creation is local, subject identity adds a separate constraint, and the
  supplied evidence does not establish arbitrary file-content exfiltration.
- Required implementation: validate `scope.target`; require relative normalized lockfile paths;
  resolve project and candidate through `realpath`; reject symlink escape; retain a second sink-side
  containment check immediately before adapter invocation.
- Failure semantics: invalid, missing or escaping evidence becomes explicit incomplete/unknown with
  a stable reason code, never silently `not_applicable`.
- Regression gate: absolute path, `..`, control character, in-project path, in-project symlink to an
  external file, and changed-target identity fixtures.

### EA-02 - unbounded member-expression naming

- Disposition: `accepted`.
- Preserve: a sufficiently deep member chain can throw `RangeError`, terminate the audit and prevent
  report creation.
- Required implementation: shared operation/depth budget for expression naming; per-module error
  isolation; typed incomplete reason retaining sanitized error class and phase.
- Regression gate: below-limit chain completes, above-limit chain produces partial coverage and exit
  3, another file in the same run remains scanned, and no stack or source content leaks.
- Patch caution: a syntax-error fixture only proves parser rejection; it does not exercise the new
  analyzer exception boundary.

### EA-03 - workspace-pattern regex execution

- Disposition: `accepted`.
- Preserve: project-controlled patterns can produce regex exceptions, excessive runtime and `?`
  overmatching that suppresses a missing-lockfile finding.
- Required implementation: bounded structural matcher or a pinned, audited glob implementation;
  declare the accepted npm/pnpm subset; reject unsupported constructs explicitly.
- Failure semantics: invalid or over-budget workspace evidence makes the lockfile rule incomplete;
  it must not silently return false and manufacture a confirmed finding.
- Regression gate: crash patterns, measured worst-case pattern, `?`, `*`, `**`, empty pattern,
  non-string input, braces/classes/extglob policy, depth/length caps and positive workspace layouts.

### EA-04 - `--fail-on never` and evidence-incomplete exit 3

- Disposition: `claim_corrected`.
- Preserve: published journey execution treats any non-zero audit exit as fatal.
- Correct boundary: `--fail-on never` disables the finding threshold; exit 3 independently means
  incomplete evidence and is already documented.
- Required implementation: make the journey runner accept and record the documented audit exit
  domain; stop only on invocation/schema/artifact failures; persist incomplete state in the journey.
- Regression gate: exit 0, exit 1/2, exit 3 and adapter-unknown matrices with expected runner state.

### EA-05 - computed Express method registrations

- Disposition: `accepted_reframed`; product correctness High, not an application Critical verdict.
- Preserve: supported-looking computed method registration can disappear while route coverage says
  completed.
- Required implementation: recognize exact statically resolvable method constants where bounded;
  otherwise emit an unsupported-registration reason and partial coverage.
- Regression gate: literal member, static const member, finite alias, dynamic user value, typo,
  optional chain and neighboring non-route property access.

### EA-06 - dependency hint upgrades empty analysis to completed

- Disposition: `accepted`.
- Preserve: framework discovery plus `eligible=0, parsed=0, incomplete=0` can produce completed.
- Required implementation: separate framework presence, eligible-source discovery and successful
  analysis; a dependency hint alone cannot prove route inventory completion.
- Regression gate: dependency-only package, worker with intentionally no routes, ignored sources,
  unsupported layout, supported empty application and mixed framework monorepo.

### EA-07 - unclassified middleware removes the route review queue

- Disposition: `accepted`.
- Preserve: an arbitrary observed middleware can count as route-scoped control and remove a route
  from `no_route_scoped_control_observed` review.
- Required implementation: keep authentication, authorization and unclassified middleware as
  independent dimensions; only classified security control changes the relevant queue.
- Regression gate: logger, parser, telemetry, rate limiter, authentication guard, authorization
  guard and combined middleware orderings.

### EA-08 - unconsumed experimental authorization finding

- Disposition: `claim_corrected`.
- Preserve: `experimentalFindings` has no stable report consumer and the experimental rule is not in
  the stable ruleset.
- Correct boundary: the same analyzer's access chains are consumed by route JSON/Markdown and expose
  missing principal constraints, RLS requirements and incomplete chains.
- Required decision: either expose the experimental finding through an explicit experimental
  contract, or delete the dead output and document accessChains as the sole surface.
- Regression gate: consumer reachability test plus capability text that does not imply zero effect.

### EA-09 - principal and tenant vocabulary divergence

- Disposition: `claim_corrected`.
- Preserve: duplicated security vocabularies can drift and need one contract test.
- Correct boundary: stable data-operation evidence already has `PRINCIPAL_KEYS`, `TENANT_KEYS` and a
  tenant constraint; the supplied claim that `tenantId` is invisible is unsupported.
- Required implementation: inventory both vocabularies, document deliberate differences, centralize
  shared semantic tokens where behavior should match, and remove stale experimental duplication.
- Regression gate: `userId`, `ownerId`, `tenantId`, `organizationId`, `orgId`, benign similarly named
  properties and aliases across both stable and experimental paths.

### EA-10 - Prisma singleton and nullish initialization

- Disposition: `accepted_reframed`; product correctness High.
- Preserve: `globalThis.prisma ?? new PrismaClient()` is not resolved, causing access chains to
  disappear.
- Required implementation: bounded recognition for the recommended singleton idiom and exact local
  aliases; unresolved client identity must degrade relevant chain coverage.
- Regression gate: direct constructor, nullish singleton, global cache assignment, import alias,
  unrelated class named PrismaClient and dynamic factory.

### EA-11 - excluded files and coverage accounting

- Disposition: `accepted_reframed`.
- Preserve: excluded production-like files are absent from incomplete counts and may be overlooked.
- Correct boundary: explicit scope exclusion is not a parser failure and should not automatically
  make every run partial.
- Required implementation: report discovered, eligible, scanned, excluded and failed counts with
  exclusion reasons; flag only ambiguous or analyzer-generated exclusions as incomplete.
- Regression gate: explicit user exclusion, generated/vendor exclusion, size/budget exclusion,
  unsupported encoding and ignored production directory.

### EA-12 - Express mount with sibling middleware

- Disposition: `accepted`.
- Preserve: `app.use(prefix, middleware, router)` attempts only one non-prefix argument as mount
  target, losing either the router relationship or middleware evidence.
- Required implementation: classify every non-prefix argument in order; resolve one exact router
  target while retaining all sibling middleware; ambiguous multiple routers fail closed.
- Regression gate: zero/one/multiple middleware, local/imported router, error middleware, arrays and
  unresolved siblings.

### EA-13 - compound innerHTML assignment

- Disposition: `accepted`.
- Preserve: `innerHTML += value` is excluded by the bare-assignment operator check.
- Required implementation: include compound assignment with the same source/sink evidence boundary;
  do not upgrade a match beyond suspected or claim input taint.
- Regression gate: `=`, `+=`, unrelated property, numeric-only benign fixture, static string,
  computed property and JSX neighbor.

### EA-14 - Next.js authorization observation boundary

- Disposition: `accepted_reframed`.
- Preserve: Next middleware/proxy and common Next-specific authorization primitives are not fully
  represented in the route-control registry.
- Correct boundary: access-chain evidence can still observe principal and tenant constraints, so
  authorization is not universally invisible.
- Required implementation: enumerate supported Next control idioms before adding detection; treat
  middleware/proxy participation as application context, not automatic per-route enforcement.
- Regression gate: App Router handlers, Server Actions, middleware/proxy matcher, Auth.js session,
  in-handler policy call and unsupported custom authorization helper.

### EA-15 - Python `verify="False"` classification

  optionally emit a separate invalid-CA-path lead only when statically justified.
- Regression gate: `False`, `True`, `"False"`, valid path string, variable, environment expression,
  numeric false and keyword aliases for supported clients.

## 6. Neighboring-defect review

The external audit exposed defect classes, not only isolated lines. Each class receives one bounded
neighbor search:

| Defect class | Search boundary | Stop condition |
|---|---|---|
| unbounded AST helper | recursive helpers reachable from project source | all have shared budget or proven bounded input |
| dynamic regex | regex constructors fed by target/scope/catalog input | input escaped, structurally matched or capped with incomplete evidence |
| false-completed coverage | all assignments to completed route/source coverage | each completion has positive eligible/analysis evidence or explicit empty-app proof |
| generic control classification | middleware/guard registry and queue predicates | authn, authz, rate limit and unclassified signals remain distinct |
| persisted-path trust | scope, baseline, catalog and adapter file inputs | realpath containment or documented operator-trusted boundary |
| renderer injection | Markdown/HTML/SARIF/JUnit fields containing project strings | context-specific encoding assertions exist |
| evidence digest drift | journey/review/release digests | volatile and semantic identities are separated |
| skip/not-run ambiguity | shell, adapter, plugin and platform tests | every intended check has a terminal accounted state |

This search is bounded to the named class and direct consumers. It is not authorization for an
unbounded refactor or a new scanner architecture.

## 7. Test budget

- One minimized reproduction and one benign neighbor per fixed mechanism.
- One plant-the-failure proof for every fix whose regression could return a false-clean result.
- Focused test files run after their owning change; no full suite per commit.
- Route matrix runs once after Phase 2; journey matrix runs once after Phase 4.
- Full `npm run check` runs once on the stable candidate and repeats only after a material code,
  generated-artifact or dependency change.
- External project applications and dependencies are not executed; only fixed source is analyzed.
- No active network security testing is in scope.

## 8. Release stop conditions

Do not publish the candidate while any condition holds:

- one project-controlled expression or workspace pattern can abort the full audit;
- a persisted lockfile path can escape through absolute, traversal or symlink resolution;
- a known unsupported route shape returns completed coverage;
- unclassified middleware suppresses route-control review;
- journey adapter identity differs between catalog, runner and reproduced evidence;
- technical Markdown can interpret a project-controlled path as markup;
- tests or public release verification report unrun work as success;
- capability or trust language exceeds the implemented default behavior;
- any of the 26 issue records lacks a disposition and closure rationale.

## 9. Required phase log format

After each phase, append:

- date and source commit;
- issues addressed and disposition changes;
- exact files changed;
- focused commands and outcomes;
- plant-the-failure result where required;
- newly discovered neighboring defects;
- remaining unknowns and owner decisions;
- whether the next phase may start.

The phase log records failures as well as passes. A failed reproduction does not erase the issue; it
changes the next experiment or narrows the claim.
