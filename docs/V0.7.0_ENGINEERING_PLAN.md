Status: active; P0-P12 complete, P13 active

`11a532ebb4166dd32ab8961e3822e54a38511fef`

Release target: v0.7.0

## 1. Product objective

v0.7.0 deepens the framework-aware route review into a bounded access-control-chain review. The
release must help a Web product owner answer five questions without claiming whole-program proof:

1. Which route-scoped authentication and authorization controls are separately visible?
2. Which application-scoped controls are present but cannot safely be attributed to every route?
3. Where does the current principal come from for supported identity providers?
4. Does a route-selected object identifier reach a supported data operation directly or through
   one statically resolved local call, and is a principal or tenant constraint visible there?
5. Which owner-controlled two-account checks should be run before describing a BOLA/IDOR defect or
   changing access-control code?

In plain language, v0.6.0 can list `PATCH /projects/:id` and show nearby guards. v0.7.0 should be
able to say that a supported Clerk/Auth.js/Better Auth/Supabase identity source was observed, that
the route identifier reaches a Prisma/Drizzle/Supabase operation through a bounded local call, and
whether the same operation visibly includes a user or tenant constraint. Missing visible evidence
remains a review state, never automatic proof of a vulnerability.

The product remains a local Skill + CLI. It does not upload source, execute project dependencies,
start the target application, sign in to user accounts, attack a deployment or edit project files.

## 2. P0 reproduced correctness defect

An external v0.6.0 audit of a NestJS monorepo reported 253 routes from 64 fully parsed controllers.
All 253 routes had identical authentication and authorization signals, and an application-level
`APP_GUARD: RateLimitGuard` appeared on every route. Seventy-two routes had no route-scoped guard;
13 were state-changing and seven were object-addressed, but they could not be separated from the
other routes by evidence state.

Code inspection reproduced the causal path:

- `globalGuardSignals()` collects every `APP_GUARD` as role `unknown`;
- `extractNestRoutes()` uses those signals as inherited route controls;
- `signalsForRole()` includes `unknown` in both authentication and authorization;
- every unknown guard is consequently duplicated into both fields for every route.

This violates the documented separation between authentication and authorization and makes an
application-scoped control look route-specific. A rate-limit guard is neither authentication nor
authorization evidence merely because it implements the Nest guard interface.

### Required v0.7.0 correction

- Application guards are inventoried once in an application-control summary. They are not copied
  into every route's authentication or authorization signals.
- Authentication and authorization signals are classified from exact package semantics or bounded
  structural evidence. An unresolved custom control is recorded once as unclassified route-control
  evidence, not duplicated into both roles.
- Every route records a route-scoped-control state:
  `classified_controls_observed`, `unclassified_control_observed` or
  `no_route_scoped_control_observed`.
- The renderer exposes a review slice for state-changing or object-addressed routes with
  `no_route_scoped_control_observed`. Expected-public login, registration and recovery routes remain
  review candidates that a human can classify; they do not become findings automatically.
- A missing visible control, including the new state, never produces a `confirmed` vulnerability.

## 3. Release thesis and scope boundary

The single product axis is access-control depth for the already supported JavaScript/TypeScript
framework boundary. v0.7.0 does not combine that work with a general framework expansion.

### Included framework surfaces

- Existing bounded Express 4/5 HTTP routes.
- Existing bounded NestJS controller routes.
- Existing bounded Next.js App Router route handlers.
- Bounded Next.js Server Actions with direct static exports and a module/function-level
  `"use server"` directive.

### Included identity-provider candidates

- Auth.js / NextAuth, including a statically resolved local `auth` export produced by `NextAuth()`.
- Better Auth, including a statically resolved local server instance produced by `betterAuth()` and
  supported server session calls.
- Clerk server identity calls from exact package imports.
- Supabase server `auth.getUser()` through a statically resolved supported client factory.
- Existing exact Passport and Nest Passport constructs.

Each provider is promoted independently. A provider stays experimental when ordinary source review
does not contain enough representative syntax or when a safe neighbour cannot be distinguished.

### Included data-access candidates

- Prisma object lookup and mutation operations.
- Drizzle query-builder and bounded `db.query.*` operations.
- Supabase `.from(...).select/insert/update/delete/upsert(...).eq(...)` chains.
- Same-handler analysis and one statically resolved local call.
- A bounded Nest constructor-injected service method only when the type/import/member relationship
  is exact; unresolved dependency injection fails closed.

### One-hop definition

One hop means exactly one project-local call edge from the entry handler or Server Action to a
named function or class method. The analyzer maps direct arguments to direct parameters and then
inspects supported operations in that callee. It does not recursively follow a second call,
evaluate runtime dependency containers or guess dynamic dispatch.

## 4. Evidence model

### 4.1 Application controls

Application-scoped controls are stored once with framework, kind, origin, source location,
classification and a boundary statement. `APP_GUARD`, global Express middleware that cannot be
ordered to a specific route, and future framework-global controls do not silently become per-route
proof.

### 4.2 Route-scoped controls

Each route or action has one scope state:

- `classified_controls_observed`: at least one supported route/controller/mount control has an
  evidence-backed authentication or authorization role;
- `unclassified_control_observed`: a route-scoped middleware, guard or helper is visible but its
  role is unresolved;
- `no_route_scoped_control_observed`: no route/controller/mount control was observed inside the
  supported static boundary.

Authentication and route authorization retain separate control states and signals. Unclassified
signals live only in the route-scoped control field.

### 4.3 Access-control chain

The chain records facts instead of a single verdict:

- identity source and provider;
- route/action object-selector source;
- data provider, model/table, operation and location;
- principal and tenant constraints observed in the supported operation;
- local call edge and mapped argument positions;
- external-policy dependency such as Supabase/Postgres RLS;
- completed, partial or not-applicable coverage with exact reason codes.

Suggested chain outcomes are:

- `principal_constraint_observed`;
- `external_policy_required`;
- `principal_constraint_not_observed`;
- `no_supported_object_operation`;
- `incomplete`.

`principal_constraint_not_observed` means only that the bounded static path did not show one. It is
not a BOLA/IDOR conclusion and remains review evidence.

### 4.4 Public artifact compatibility

The v0.6.0 route artifact has `additionalProperties: false`; silently adding fields would break old
validators. v0.7.0 therefore introduces `route-security-v2.schema.json`, keeps the same public file
names, records `schemaVersion: 2`, and treats v1 route baselines as explicitly not comparable.

The v2 document adds application controls, route-scoped-control state, bounded access chains and
Server Actions as a separate surface collection. It does not encode Server Actions as fictional
HTTP methods or URLs.

## 5. User-facing behavior

The Markdown report must place the high-signal review queue before the full inventory:

- state-changing or object-addressed routes with no route-scoped control;
- access chains where a request-selected object reaches a supported operation and a principal or
  tenant constraint was not observed;
- incomplete chains where a user could otherwise mistake missing analysis for a clean result;
- expected-public routes remain in the queue until the owner classifies them.

Every access-chain review item includes:

- industry term and plain-language meaning;
- what source fact was observed;
- what the analyzer did not prove;
- realistic consequence if project review confirms a defect;
- proposed inspection or change boundary;
- likely side effects, including valid sharing/admin/support flows;
- unauthenticated, owner, non-owner and lower-role test suggestions;
- normal functional retest and rollback criteria.

No credential, request body, source snippet, absolute path, token or user data is persisted.

## 6. Regression and CI behavior

Route baseline comparison gains explicit access-control degradation reasons without inventing a
vulnerability state:

- classified authentication disappeared;
- classified route authorization disappeared;
- route-scoped control became absent or unclassified;
- a principal/tenant query constraint disappeared;
- a previously complete access chain became incomplete;
- a new state-changing/object-addressed unclassified route appeared.

The default command reports these changes. A new explicit route-regression gate may return a
non-zero policy result only when the caller opts in. Evidence-incomplete states retain exit 3 and
cannot be overridden into a pass. Initial audits do not fail merely because expected-public routes
need classification.

## 7. Non-goals

v0.7.0 does not include:

- Strix, MCP, DAST, browser automation or authenticated crawling;
- automatic exploitation, live two-account testing or credential handling;
- unattended patches or automatic authorization changes;
- whole-program or multi-service taint analysis;
- more than one project-local call edge;
- Hono, Fastify, tRPC, GraphQL, Next Pages Router or Python framework expansion;
- automatic evaluation of database RLS, IAM or runtime middleware order;
- name-only classification such as treating `RateLimitGuard`, `JwtAuthGuard` or `RolesGuard` as
  proof based on their class names;
- representative production precision/recall claims;
- marketing, social-preview or listing work as a release gate.

## 8. Validation budget

Validation must be proportional and must not become another oversized self-authored benchmark.

- One minimized Nest global-guard fixture reproduces the 253-route failure shape with a small route
  count and exact signal-count assertions.
- Every promoted provider/data operation has a positive, a benign neighbour and an incomplete
  case.
- One plant-the-failure check is required for each defect class that could silently regress.
- Ordinary-source review is capped at four or five fixed public commits and 30-50 manually examined
  access-control chains total.
- The review records misses, extras and ambiguous cases; it publishes no production accuracy score.
- One clean-room npx run, one verified Skill install and one immutable Action consumer are enough
  for distribution parity unless a channel-specific failure appears.
- Do not rerun the full suite after an identical tested tree merely to create duplicate evidence.

## 10. Stop conditions

Stop implementation or keep a capability experimental when:

- a provider can only be recognized by function, variable or class name;
- one-hop resolution silently crosses more than one edge;
- a missing global or route control would be rendered as a confirmed defect;
- a Server Action must be represented as a guessed URL;
- a data-provider adapter cannot distinguish a constant/safe neighbour from request-selected data;
- external-policy/RLS uncertainty would be displayed as absent protection;
- schema migration could make a v1 baseline appear comparable;
- installation channels would execute different analyzer code;
- validation effort grows beyond the bounded review without a demonstrated defect requiring it.

## 11. Definition of done

v0.7.0 is complete only when:

- the Nest global-guard/auth-authz aggregation defect is fixed and regression-protected;
- route-scoped absence is directly filterable without creating a vulnerability claim;
- at least two identity-provider families and two data-provider families pass stable promotion, with
  the remaining implemented families honestly experimental if necessary;
- direct and one-hop access chains preserve complete/partial boundaries;
- supported Server Actions are represented separately from HTTP routes;
- ordinary-language review and two-account verification guidance ship;
- v1 route baselines are explicitly not comparable to v2;
- tests, lint, Skill validation, package inspection, CI and CodeQL pass on the release source;
- signed GitHub Release, npm provenance, clean-room npx/Skill/Action consumers and signed `v1`
  promotion are publicly verified;
- this document records every phase outcome, deviation and residual limitation.
