# v0.6.0 framework-aware route security engineering plan

Status: completed; P0-P14 completed

Plan date: 2026-08-24

Baseline: published v0.5.4 at `2fde113cd58b3465067a8de33a28ff4fe8f7fda5`

Release target: v0.6.0

## 1. Product objective

v0.6.0 is the first framework-aware application-security release. Its purpose is to move the
automatic first pass from isolated file-level constructs toward the HTTP boundary that a Web
product actually exposes.

The release must answer four bounded questions for supported JavaScript/TypeScript frameworks:

1. Which HTTP routes can be statically inventoried, with method, path, framework and source
   location?
2. Which authentication or authorization control signals are visible locally or inherited through
   a supported framework construct?
3. Which state-changing or object-addressed routes should be reviewed first because a required
   control was not observed or could not be resolved?
4. Which direct object lookup patterns create a concrete BOLA/IDOR review lead without claiming
   that exploitation, reachability or missing authorization has been proved?

In plain language, v0.5.4 can say "this file calls a dangerous API." v0.6.0 should additionally say
"this is the `PATCH /projects/:id` route, it changes data, an authentication signal is visible, but
the object-level ownership check is still unresolved; inspect this query and service call first."

The release remains a local Skill + CLI. It does not upload source, start the target application,
attack a live service or modify project files.

## 2. Why this is the v0.6.0 axis

The v0.5.4 baseline already has:

- 25 built-in risk rules and two evidence-integrity rules;
- 16 opt-in external-adapter rules, including same-file Opengrep request flows;
- 43 stable rules in total;
- Git-aware full, `--since` and `--staged` source scopes;
- professional and plain-language explanations, repair proposals, dual retests and rollback;
- report/baseline evidence contracts and distribution through npm, Claude plugin, verified archive
  and GitHub Action.

The main remaining product gap is not another release ceremony or another set of configuration
patterns. The built-in detector does not currently model route entry points, control inheritance or
object-level authorization review. Those are central to Web products and to users who do not know
where to start a manual security review.

This plan therefore spends the v0.6.0 complexity budget on one capability family:

> JavaScript/TypeScript framework-aware route inventory, control-evidence mapping and prioritized
> authorization review.

## 3. Scope decisions requiring owner approval

Implementation must not start until D0 is approved. D1 and D2 are promotion decisions made from
evidence during the milestone, not assumed in advance.

### D0 - parser and distribution architecture

Recommended decision: use an exact-version MIT-licensed JavaScript/TypeScript parser behind a small
project-owned adapter and ship a reproducibly generated self-contained parser bundle.

The initial candidate is `@babel/parser`, because it covers modern JavaScript, TypeScript, JSX and
legacy/current decorators in one parser. The version must be pinned exactly after a Node 22-24
compatibility check. As of the plan date, the registry reports `@babel/parser` 8.0.4 as MIT licensed;
the implementation phase must recheck its engine, dependency and license metadata before pinning.

Why the bundle is required:

- npm/npx can install runtime dependencies, but the verified GitHub archive and agent-skill install
  paths currently run from copied files without `npm install`;
- a normal runtime dependency would create different detector capability by installation channel;
- a checked-in generated bundle keeps runtime behavior self-contained while its source version,
  digest, license and regeneration command stay reviewable.

The bundle must not contain route rules. It contains parser runtime only. Framework interpretation
remains in readable project-owned modules and tests.

Rejected for v0.6.0:

- extending the hand-written tokenizer into a general AST, because every framework feature would
  add more syntax ambiguity and repeat the parser-maintenance problem;
- `oxc-parser` as the default, because platform-native optional binaries complicate the verified
  archive, Claude plugin and Action parity;
- Acorn alone, because TypeScript and decorator support would require more plugin contracts;
- caller-installed parser dependencies, because missing parser evidence would make the headline
  capability unavailable for a normal Skill installation.

Owner decision: approve the self-contained parser-bundle route, or return the plan for a narrower
tokenizer-only redesign. This is the one decision that materially changes implementation and
distribution.

### D1 - stable framework boundary

Proposed stable inventory boundary:

- Express 4/5 direct application and router registrations;
- NestJS controller and HTTP method decorators;
- Next.js App Router `app/**/route.{js,jsx,ts,tsx}` method exports.

Pages Router API routes, Fastify, Hono, Koa, tRPC, GraphQL resolvers and Python frameworks remain
outside the stable v0.6.0 boundary. A framework extractor that misses its contract or ordinary-code
review gate remains `experimental` and is not counted as stable.

### D2 - BOLA review rule promotion

The object-authorization review rule starts `experimental`. It becomes stable only if its exact
direct-query boundary survives the ordinary-project review in Phase 9. Route inventory can still
ship if this risk rule remains experimental.

The release must not preserve a misleading rule merely to increase the stable count.

## 4. Non-goals

v0.6.0 does not include:

- Strix as a scanner, dependency, subprocess, benchmark authority or product label;
- MCP server or a second execution transport;
- whole-program, inter-service or runtime data-flow analysis;
- automatic proof that a route is exploitable, authenticated, authorized or reachable in
  production;
- automatic BOLA/IDOR exploitation or requests against a live target;
- dynamic application security testing, browser automation or authenticated crawling;
- Python AST migration or Python framework route inventory;
- automatic project edits, unattended fixes or merge-ready patches without owner review;
- broad file-upload, CSRF, rate-limit, OAuth, GraphQL or LLM rule packs;
- Java, Go, Ruby, PHP or Rust source-depth expansion;
- Social Preview repair as a release gate;
- new marketing workflow, listing submission or release-process redesign;
- a report schema migration solely to hold route inventory;
- a representative production precision/recall claim.

These exclusions prevent one minor version from simultaneously becoming a parser migration, a
multi-language SAST engine, a DAST scanner and an auto-fixer.

## 5. Threat and user model

### 5.1 Intended user

The primary user can build and deploy a Web product with an AI coding agent but may not know how
authentication differs from authorization, why `GET /users/:id` can be a BOLA boundary, or where
middleware inheritance changes the conclusion.

Output must retain industry terms while explaining:

- what the route does;
- what control signal was actually observed;
- what was not proved;
- what can happen if the missing review confirms a defect;
- what change is proposed;
- which valid product flows the change can break;
- how to run the security retest and normal functional retest;
- when to roll back.

### 5.2 Adversary and failure model

The relevant attacker is an unauthenticated or lower-privileged caller attempting to:

- call a state-changing endpoint;
- substitute another user's object identifier;
- reach an endpoint that relies on an absent or bypassed access-control layer;
- exploit a route whose sensitive operation was difficult to prioritize in file-only output.

The detector itself must also resist these failure modes:

- valid source syntax causes a route file to disappear silently;
- dynamic or unresolved routing is reported as completed coverage;
- a middleware name is treated as proof of authentication;
- authentication evidence is treated as proof of object-level authorization;
- a global or parent guard is ignored and creates a noisy missing-control claim;
- an explicit public override is ignored;
- a parser error becomes a clean report;
- source snippets, secrets, absolute paths or request values leak into route artifacts;
- changing installation channel changes the parser or route results.

## 6. Evidence semantics

Route evidence uses observed facts and unresolved review states. It must not overload the existing
finding states.

### 6.1 Route identity

Each route record contains:

- framework and framework adapter revision;
- normalized HTTP method;
- static normalized path when available;
- source-relative path and declaration line;
- handler symbol when statically available;
- route fingerprint derived from framework, method, normalized path, declaration role and a
  sanitized structural discriminator;
- state-changing classification;
- object-addressed classification;
- parser and framework-extractor coverage references.

Dynamic paths remain represented as unresolved routes; they are not omitted and are not converted
to guessed strings.

### 6.2 Control evidence vocabulary

Authentication and authorization are recorded separately with one of these states:

- `local_observed`: an exact supported construct is attached to or called in the handler;
- `inherited_observed`: an exact supported parent, router, controller or global construct maps to
  the route through a completed supported relationship;
- `candidate_observed`: a custom middleware, guard or helper is visible but its behavior is not
  established;
- `not_observed`: analysis completed within the documented boundary and found no supported signal;
- `incomplete`: parsing, module linking, dynamic registration or inheritance resolution prevented
  a conclusion;
- `not_applicable`: the control question does not apply under a documented exact condition.

`not_observed` means only that this static detector did not see a supported signal. It is not
synonymous with "missing in production" and never creates a `confirmed` vulnerability.

### 6.3 Review priority

Priority is workflow ordering, not vulnerability severity:

- `review_first`: state-changing or object-addressed route plus a direct sensitive operation and
  unresolved authorization evidence;
- `review_next`: state-changing route with authentication/authorization not observed, or an
  object-addressed route whose data access is delegated outside the analysable handler;
- `review_later`: read-only route with unresolved controls and no direct sensitive operation;
- `no_automatic_priority`: sufficient evidence for inventory but no supported reason to rank it.

The renderer must state this distinction next to the priority summary.

### 6.4 Finding states

Framework-aware source matches remain `suspected` unless a future rule proves a narrower static
fact. Parser, route-linking or inheritance failure becomes `source-evidence-incomplete / unknown`
or an equivalent dedicated evidence-integrity finding. Unavailable evidence never produces a pass.

## 7. Supported syntax contract

### 7.1 Express 4/5

Stable candidates:

- `app.get('/path', handler)` and other standard HTTP methods;
- `router.get('/path', middleware, handler)`;
- `app.route('/path').get(handler).post(handler)`;
- statically resolvable `app.use('/prefix', router)` and router-to-router mounts through local
  relative imports;
- ordered `router.use(exactKnownControl)` inheritance when both registration and route ordering are
  statically available;
- arrays of direct middleware expressions;
- exact known-package control imports recorded by package and imported binding.

Incomplete or experimental:

- computed method names, computed paths, loop-generated routes, runtime plugin registration;
- non-local package routers, dependency-injected routers or mutation through arbitrary aliases;
- path concatenation beyond static literals and static template segments;
- behavior inferred only from a custom function name.

### 7.2 NestJS

Stable candidates:

- `@Controller()` class prefix;
- `@Get`, `@Post`, `@Put`, `@Patch`, `@Delete`, `@Options`, `@Head` method decorators;
- class-level and method-level `@UseGuards` candidates;
- Passport `AuthGuard(...)` constructs and exact supported package imports;
- `APP_GUARD` providers when the provider relationship is statically resolvable;
- explicit public/bypass decorators as a recorded override candidate, never silently ignored;
- static decorator strings and string arrays where the framework supports them.

Incomplete or experimental:

- custom decorators whose implementation cannot be resolved locally;
- module factories, dynamic modules and providers created at runtime;
- guards whose authentication/authorization role depends only on class names;
- GraphQL resolvers, gateways and microservice message handlers.

### 7.3 Next.js App Router

Stable candidates:

- route files under a discovered `app` or `src/app` root;
- exported `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS` and `HEAD` functions;
- default/static segments, `[id]`, `[...slug]`, `[[...slug]]`, route groups and private folders in
  normalized path construction;
- direct supported authentication/session calls whose imported package and binding are exact;
- direct object identifier use in the same exported handler when the experimental BOLA rule's
  strict contract is met.

Incomplete or experimental:

- Pages Router API handlers;
- middleware matcher semantics beyond exact static matcher forms;
- wrappers re-exported from another package or dynamic handler factories;
- authorization enforced only in a downstream service, database policy or reverse proxy.

## 8. Artifact and compatibility design

### 8.1 Route artifact

Do not force the route inventory into report v3 findings or migrate the report schema for this
release. Add a versioned companion artifact:

- `route-security.json`, validated by `docs/route-security-v1.schema.json`;
- `route-security.md`, rendered from exactly the JSON bytes held in memory;
- optional escaped `route-security.html` only if it reuses the existing safe renderer primitives
  without expanding the schedule.

The artifact contains summary, coverage, routes, control evidence, priorities and limitations. It
contains no source snippets, absolute paths, secrets, headers, cookies or environment values.

The normal audit console and README example point to both `report.md` and `route-security.md`.
Existing report v3 remains compatible. Route analyzer coverage is also represented in report v3's
normal coverage ledger so parser/extractor failure can affect exit 3.

### 8.2 Baseline and retest

v0.6.0 does not pretend that route identity is proven across arbitrary refactors. The companion
artifact supports a bounded comparison:

- same framework, method, normalized path and compatible analyzer revision: comparable;
- exact route disappearance after completed coverage: `removed`;
- exact route appearance: `added`;
- control evidence changes: `changed` with prior/current states;
- parser or extractor incomplete: `unretested`, never removed or improved;
- ambiguous dynamic paths or duplicate structural identities: `not_comparable`.

Route comparison does not change the existing finding baseline contract. A route becoming
`local_observed` is not proof that authorization is correct; the renderer calls it an observed
control change.

### 8.3 Incremental modes

`--since` and `--staged` keep whole-project route context while filtering user-facing route changes:

- analyse required manifests, mounts, controllers, middleware and global guards from the complete
  selected Git snapshot;
- show routes added or changed by the diff;
- retain inherited-control context from unchanged files;
- explicitly count untracked or unstaged exclusions using the existing semantics;
- never analyse only changed lines when doing so would break route/control linkage.

This keeps incremental mode a noise filter rather than a weakened parser traversal.

## 9. Proposed rule inventory

The route inventory and coverage ledger are capabilities, not risk-rule count. Only the following
rules are candidates for v0.6.0.

### 9.1 `js-route-object-authorization-review`

Initial maturity: `experimental`

Default state: `suspected`

Default severity: `high`

Trigger boundary:

- a supported route contains a static object identifier segment;
- the handler reads that route identifier;
- the same handler directly constructs a supported ORM/repository lookup or mutation keyed by the
  identifier;
- no supported local principal/owner/tenant constraint is present in that same operation;
- analysis of the handler and operation completed.

Initial supported direct operations should be deliberately narrow: Prisma calls first. TypeORM or
Mongoose enter only if their positive, safe-neighbour and ordinary-project evidence fits the same
phase budget.

What it proves: a request-selected object identifier reaches a direct supported data operation and
the detector did not observe a supported principal constraint in that operation.

What it does not prove: missing authorization, route reachability, user privilege, service-layer
checks, database row-level security, policy middleware or exploitability.

Plain-language output must say: "This route lets the caller select a record ID and directly uses it
in a database operation. The tool could not see an owner, tenant or permission constraint in that
operation. A check may exist elsewhere, so review before changing code."

Promotion gate:

- no known safe-neighbour contract failure;
- all matches in the bounded ordinary-project review manually classified;
- recurring wrapper/service/RLS cases are either excluded structurally or documented prominently;
- if the rule mainly repeats unresolved cases without actionable location evidence, keep it
  experimental and omit it from default findings.

### 9.2 `js-route-security-evidence-incomplete`

Kind: `evidence_integrity`

Default state: `unknown`

This is emitted only when an eligible supported-framework file or required relationship cannot be
parsed or resolved within a contract that otherwise applies. It aggregates sanitized reason codes
and bounded sample paths. Dynamic routes that are explicitly outside the stable syntax contract
are counted as incomplete coverage, not silently ignored.

### 9.3 Deferred candidates

These remain out of the stable v0.6.0 count unless a later plan replaces scope:

- state-changing route with no visible auth as a risk finding;
- generic auth middleware-name matching;
- missing CSRF protection;
- missing route-level rate limiting;
- upload size/type/storage policy;
- GraphQL resolver authorization;
- automatic service-layer or database-policy proof.

They can appear as route-ledger review questions, not as vulnerability findings.

## 13. Risk register and rollback

| Risk | Consequence | Control | Rollback |
|---|---|---|---|
| Parser bundle breaks install parity | Headline capability differs by channel | Reproducible bundle and clean-room parity gate | Remove route capability and parser artifacts; retain v0.5.4 tokenizer path |
| Package grows materially | Slower install and larger trust surface | Record packed delta; owner review above 2 MiB | Defer bundled AST and redesign a narrower tokenizer-only milestone |
| Route inventory overcounts lookalikes | User wastes time on non-routes | Exact import/binding checks and safe neighbours | Keep affected extractor experimental or remove syntax family |
| Route inventory silently misses dynamic routes | False sense of coverage | Incomplete reason codes and unknown exit | Downgrade framework maturity; do not advertise stable coverage |
| Custom middleware name is treated as auth | False assurance | Candidate state separate from exact observed state | Remove name heuristics; keep only exact package/binding evidence |
| Authentication is confused with authorization | BOLA risk hidden | Separate authn/authz fields and no propagation between them | Revert control mapping revision and mark routes unresolved |
| Global control is ignored | Noisy missing-control review | Exact inheritance/link tests | Keep relationship incomplete instead of not_observed |
| BOLA rule has wrapper/RLS noise | High-severity alert fatigue | Direct-query-only experimental gate and ordinary review | Do not promote; retain route-ledger review priority only |
| Route artifact breaks report consumers | Existing integrations fail | Companion schema, unchanged report v3 | Disable companion generation without migrating report v3 |
| Baseline claims improvement on incomplete scan | False fixed signal | Route-specific unretested state | Disable route comparison while retaining current inventory |
| Third-party parser vulnerability/license change | Supply-chain exposure | Exact pin, integrity, SBOM, notice, CodeQL/advisory review | Pin prior reviewed parser or remove capability in a patch |
| Scope expands into six frameworks | Unfinished and weak extractors | Per-framework D1 gates and explicit non-goals | Ship only extractors that pass; leave others experimental |

## 16. Expected v0.6.0 outcome in plain language

If all stable gates pass, a normal user should receive two connected views:

1. the existing finding report, which lists concrete configuration, source and adapter leads;
2. a route-security review, which lists the supported endpoints, shows where recognizable controls
   were seen, separates login from object-level authorization, and puts risky review work in a
   useful order.

The tool still will not say "your application is secure" or "BOLA is confirmed" from source alone.
It will reduce the amount of security expertise needed to find the correct routes, ask the correct
authorization questions and avoid fixing the wrong layer first.
