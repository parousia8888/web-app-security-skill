# v0.7.2 correctness and trust-boundary patch plan

Status: active; Phases 0-7 complete; Phase 8 pending

`2b746b168d767c9b2225a273474e561650b2b6f8`; baseline public-state commit

Release target: v0.7.2

## 1. Objective

v0.7.2 is a bounded correctness release. It closes three reproduced false-clean or destructive
paths, makes the shipped JSON schemas independently executable in CI, makes the v0.7.0 ordinary
source review recomputable from project records, and corrects public trust language.

The release does not add a new framework, external scanner, active probe, automatic patcher or
production accuracy claim. Focused tests run during implementation; the full repository gate runs
once against the final candidate.

## 2. Reproduced baseline

### 2.1 Demo output ownership

`scripts/demo.mjs` resolves `--out` and immediately calls
`rmSync(out, { recursive: true, force: true })`. There is no ownership marker, protected-path
check, symlink rejection or child allowlist. A missing value after `--out` reaches `resolve()` with
an invalid argument instead of returning the CLI usage exit code 2.

### 2.2 Evidence redaction

The current exact-key expression recognizes only singular, separator-specific names. The following
keys can retain a sentinel in sanitized technical evidence:

`tokens`, `secrets`, `passwords`, `api_keys`, `credential`, `credentials`, `accessToken` and
`access_tokens`.

The reproduced affected outputs are `report.json`, technical Markdown and any additional JSON that
uses the same sanitized evidence tree. Normal Markdown, HTML, SARIF and JUnit currently omit or
sanitize the tested sentinel through their own projections. v0.7.2 nevertheless asserts every
shareable renderer independently.

### 2.3 Express extraction matrix

The bounded parser currently produces:

| Shape | Routes | Coverage | Exit implication |
|---|---:|---|---:|
| inline CommonJS | 3 | completed | 0 |
| split CommonJS with a variable-bound router | 3 | completed | 0 |
| split ESM | 3 | completed | 0 |
| direct `require('express').Router()` | 0 | completed | 0 |
| imported `registerRoutes(app)` | 0 | completed | 0 |

The first three cases correct an over-broad external claim that all cross-module Express routing
fails. The last two are genuine false-clean paths. An Express worker with no HTTP routes remains a
valid completed result, so `routes.length === 0` is not a safe failure rule.

### 2.4 Schema enforcement

Handwritten report, finding and route validators exist. The reproduced gaps are narrower:

- a valid report with an unexpected top-level property can pass a handwritten validator even when
  its JSON Schema declares `additionalProperties: false`;
- schema `$id` values use GitHub `blob` URLs that return HTML rather than schema JSON;
- a v1-shaped finding passed to a newer validator produces ordinary errors as intended;
- some `null` or other JSON-shaped inputs can throw while validation should return an error list.

### 2.5 Review provenance

`scripts/generate-v070-access-review.mjs` stores both project records and a hand-written aggregate.
The published `173` route count is arithmetically consistent with the current records, but the
checker does not recompute all route, action and chain totals and the records do not contain the
tool commit, exact command or report digest needed for offline provenance verification.

### 2.6 Release identity

The intended public invariant is:

`release tag source commit = npm gitHead = GitHub Release source = immutable Action commit`.

`main` may contain later verifier, bootstrap and public-state commits. The repository-local
`.github/release-signers` file verifies consistency with a key checked into the same repository; it
does not independently establish GitHub account ownership. GitHub signature status and npm OIDC
provenance are separate trust signals.

## 4. Release stop conditions

Do not publish v0.7.2 if any condition is true:

- a supported Express fixture can return a false-clean result;
- the sensitive sentinel appears in any shareable artifact;
- the demo can touch a pre-existing unowned directory or child;
- Ajv and handwritten validators disagree on the curated overlap corpus;
- the access-review aggregate remains independently hardcoded;
- npm `gitHead` differs from the `v0.7.2` tag source commit.

## 5. Validation budget

- Run focused tests after the phase that owns them.
- Require one machine assertion and one plant-the-failure proof for every silently reversible fix.
- Use only minimized local fixtures for the P0 fixes.
- Run the full repository gate once after the implementation and documentation tree is final.
- Repeat a full gate only if the tested tree changes materially or a release-channel check exposes
  a channel-specific defect.
