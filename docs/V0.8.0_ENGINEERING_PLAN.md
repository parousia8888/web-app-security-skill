# v0.8.0 bounded interprocedural access-control engineering plan

Status: active; P0-P15, D1 and D2 complete, P16 in progress

Plan date: 2026-08-29

Baseline: published v0.7.3; final public-state commit
`0cab0b680fbb39d51125dece1ea09dca6578b908`

Release target: v0.8.0

## 1. Product objective

v0.8.0 deepens the existing JavaScript/TypeScript route review from same-handler and one-local-call
evidence into a bounded interprocedural access-control analysis. The release should help a Web
product owner answer six questions without claiming whole-program proof:

1. Which client-selected object identifier entered the route or Server Action, and from which
   request surface?
2. Which exact local functions, service methods or repository methods received that value?
3. Where did the current principal or tenant value come from, and did it travel along the same
   resolved path?
4. Which supported Prisma or Drizzle operation used the object identifier?
5. Was a principal, tenant, ownership comparison or explicit external-policy dependency visible on
   that bounded path?
6. Where did analysis stop, and what must a human or authorized two-account test verify next?

In plain language, v0.7.3 can often say:

> `GET /projects/:id` is object-addressed, a user identity is visible and the selected ID enters a
> service call, but analysis stops before the next local call.

v0.8.0 should be able to say, when exact source relationships permit:

> The `projectId` selected by the request moves from the controller to `ProjectService.find`, then
> to `ProjectRepository.findForUser`. The current user's ID travels through the same calls and is
> used as `ownerId` in the Prisma `where` condition. This is static source evidence; deployed
> enforcement and non-owner denial still require a retest.

For an unconstrained path, it should say:

> The request-selected ID reaches `prisma.project.findUnique({ where: { id } })`. No principal or
> tenant constraint was observed on the supported path. This is a review lead, not proof that a
> non-owner can retrieve the record.

The product remains a local Skill + CLI. It does not upload source, execute project dependencies,
start the target application, sign in to user accounts, attack a deployment or edit project files.

## 2. Why this is the v0.8.0 axis

### 2.1 Current shipped strengths

The v0.7.3 baseline already contains the infrastructure needed for this work:

- a pinned `@babel/parser` bundle and bounded AST walker;
- deterministic JavaScript/TypeScript module discovery and exact relative, alias and workspace
  resolution;
- Express, NestJS and Next.js App Router inventory plus Next.js Server Actions;
- separate route authentication, route authorization and object-authorization evidence;
- exact bounded Nest Passport and Auth.js identity evidence;
- bounded Prisma and Drizzle data-operation evidence;
- same-handler and one exact local-call access chains;
- deterministic source and module-graph budgets with fail-closed coverage;
- route-security JSON, Markdown, digest, baseline and regression artifacts;
- four-state finding semantics, plain-language explanation and retest guidance.

The release must reuse these components. It must not add a second parser, duplicate the CLI runtime
or create a parallel access-chain artifact.

### 2.2 Current measured gap

The fixed-commit v0.7.0 review inventories 173 HTTP routes and 23 Server Actions across four public
projects. Thirty-two entries were manually examined. The review records 12 partial chains and zero
completed ordinary-project chains.

The observed misses cluster into three product-relevant families:

1. **Selector origin gaps:** query parameters, JSON body fields and some Server Action argument
   shapes are not modeled as client-selected object identifiers.
2. **Callable resolution gaps:** local re-exports, handler wrappers and exact repository/service
   relationships stop before the underlying implementation.
3. **Depth and propagation gaps:** analysis stops before a second local call and cannot preserve
   object, principal or tenant meaning through common parameter and return shapes.

Those gaps prevent the existing identity and database evidence from joining into useful ordinary
project paths. Additional unrelated source patterns would not close this gap.

### 2.3 Standards relationship

The release is guided at the category level by:

- OWASP API Security Top 10 2023 API1, Broken Object Level Authorization;
- OWASP API Security Top 10 2023 API5, Broken Function Level Authorization, only where existing
  route-control evidence participates in review priority;
- OWASP ASVS 5.0 access-control requirements;
- CWE-639, Authorization Bypass Through User-Controlled Key;
- CWE-862 and CWE-863, missing or incorrect authorization.

These mappings classify the review problem. They do not turn a static chain into a confirmed CWE,
ASVS failure or exploitable vulnerability.

## 3. Release thesis

The single product axis is deeper, more useful access-control evidence for already supported
JavaScript/TypeScript Web surfaces.

v0.8.0 succeeds when it can follow exact ordinary controller/service/repository paths, preserve the
meaning of object/principal/tenant values, describe visible enforcement evidence and stop honestly
at ambiguity. It does not succeed merely because a larger number of routes, rules or providers is
listed.

The implementation model is a bounded access slice:

```text
request selector / Server Action argument
        |
        v
route handler or action
        |
        v
exact local callable edge 1
        |
        v
exact local callable edge 2 ... edge 4
        |
        +--> supported Prisma / Drizzle operation
        |
        +--> exact owner / principal / tenant comparison evidence
```

This is deliberately smaller than global data-flow analysis. It follows only exact project-local
symbols from a known Web entry point, under deterministic limits, toward supported access-control
sinks.

## 4. Included scope

### 4.1 Entry surfaces

- Existing bounded Express 4/5 route handlers.
- Existing bounded NestJS controller methods.
- Existing bounded Next.js App Router route handlers.
- Existing bounded Next.js Server Actions.

No framework is added merely to raise coverage counts.

### 4.2 Selector origins

The following client-controlled candidates enter the v0.8.0 selector model only when their field
name and source expression are statically exact:

- Express `req.params.<id>`, `req.query.<id>` and `req.body.<id>`;
- destructured Express `params`, `query` and `body` containers;
- Nest `@Param()`, `@Param('<id>')`, `@Query()`, `@Query('<id>')`, `@Body()` and exact DTO/property
  access visible in the handler;
- Next.js App Router context `params`, including an exactly awaited params object;
- `request.nextUrl.searchParams.get('<id>')`;
- `new URL(request.url).searchParams.get('<id>')` when the URL receiver is the exact handler
  request;
- one exactly awaited `request.json()` result followed by direct property access or object
  destructuring;
- Next.js Server Action direct parameters and exact `FormData.get('<id>')` fields.

Candidate names remain intentionally narrow: `id`, `*Id`, `*_id` and the exact dynamic route
segment name. Generic strings, search terms, slugs and tokens are not silently treated as protected
object identifiers.

The artifact records the selector field name and source location. It never records the runtime
value, request body or source snippet.

### 4.3 Identity and tenancy

- Preserve stable Nest Passport and Auth.js identity evidence.
- Preserve experimental Clerk, Better Auth and Supabase boundaries without automatic promotion.
- Follow an exact principal or tenant value through supported local parameter mappings.
- Observe identity retrieval inside a resolved callee when the provider primitive is exact.
- Keep principal and tenant facts separate throughout the path.
- Do not infer identity from names such as `user`, `session`, `auth` or `currentUser` without a
  supported source relationship.

### 4.4 Local callable edges

Supported edges are limited to exact project-local relationships:

- same-file named function calls;
- exact named/default imports resolved to one local module export;
- exact local re-export chains;
- exact class methods on a statically identified local instance;
- exact Nest constructor-injected service methods where imported type, constructor property and
  method resolve uniquely;
- exact static member calls supported by the callable index;
- an exact `react` `cache(callback)` binding when the imported cache identity and its single local
  callback target are both unique; this exposes the callback body but does not classify cache as
  authentication or authorization;
- a statically visible underlying handler passed to a local wrapper, while wrapper enforcement
  remains separately unresolved unless its behavior is proved by supported structure.

The initial stable depth limit is four local call edges from the route/action entry. Four edges cover
common handler -> service -> repository -> helper layouts while bounding combinatorial growth.

### 4.5 Data providers and policy evidence

Stable candidate paths remain limited to Prisma and Drizzle. Supabase remains experimental because
database RLS is external evidence.

The release may observe four evidence families:

1. object selector used in the supported data operation;
2. principal or tenant constraint in the data operation;
3. exact post-load owner or tenant comparison involving the returned object and current principal;
4. explicit external-policy dependency such as Supabase/Postgres RLS.

A comparison is evidence only when both operands resolve to supported facts. A function name such as
`canAccess`, `authorize`, `checkPermission` or `isOwner` is never sufficient by itself.

## 5. Explicit non-goals

v0.8.0 does not include:

- Strix or any scanner-as-a-service dependency;
- MCP, a remote service, repository upload or another transport runtime;
- authenticated DAST, browser automation or live two-account testing;
- automatic exploitation or a confirmed BOLA/IDOR verdict;
- unattended patches or CLI writes to audited project source;
- whole-program, whole-repository or multi-service taint analysis;
- dynamic dispatch, runtime dependency containers, reflection, proxies or monkey patching;
- arbitrary callback, closure, generator, event-bus or queue flow;
- arbitrary higher-order wrapper transparency beyond the exact React `cache(callback)` shape
  approved at D1;
- array indexing, rest, transformation or ambiguous element identity beyond one direct
  single-element destructuring binding from an exact supported operation;
- optional or dynamic data-client fallbacks unless exact argument mapping proves the transaction
  parameter was omitted and the local expression is exactly `tx ?? prisma`;
- Hono, Fastify, tRPC, GraphQL, Next Pages Router or Python framework expansion;
- TypeORM, Sequelize, Mongoose, raw SQL or a new ORM family;
- automatic evaluation of RLS policies, IAM, middleware runtime order or deployed configuration;
- name-only classification of wrappers, authorization helpers, guards, roles or ownership checks;
- generic secret, XSS, SQL injection or source-rule count expansion;
- production precision/recall, reachability or exploitability claims;
- marketing publication, social-preview work or listing submissions as a product gate.

If a real evaluation case depends on one of these surfaces, it is recorded as excluded or partial.
The case is not removed to improve the completion ratio.

## 6. Capability and evidence contract

### 6.1 Meaning of a completed access path

`completed` means all of the following are true for one bounded static path:

- the Web entry handler or Server Action is identified exactly;
- at least one client-selected object fact is identified exactly;
- every recorded local call edge resolves to one callable target;
- argument, property and return mappings used by the path are supported and unambiguous;
- the path reaches a supported data operation or supported ownership-comparison terminal;
- no analysis budget needed by that path was exhausted;
- every relevant file on that path parsed successfully.

`completed` does not mean the route is secure, vulnerable, reachable, deployed or correctly
configured. The renderer must state this immediately beside the status.

### 6.2 Meaning of a partial access path

`partial` means a relevant path lead was observed but at least one required relationship was not
resolved. Each partial path has one primary reason code and may carry supporting limitation codes.

Required primary reason families include:

- `call_depth_limit_reached`;
- `call_state_budget_reached`;
- `call_target_unresolved`;
- `call_target_ambiguous`;
- `dynamic_dispatch_unresolved`;
- `reexport_unresolved`;
- `wrapper_handler_unresolved`;
- `argument_mapping_ambiguous`;
- `destructuring_mapping_ambiguous`;
- `return_mapping_unresolved`;
- `selector_source_unresolved`;
- `identity_source_unresolved`;
- `data_client_unresolved`;
- `constraint_expression_unresolved`;
- `module_or_parser_evidence_incomplete`.

Unavailable evidence never becomes `not_applicable`, `completed` or a clean result.

### 6.3 Outcome model

The v3 route artifact uses outcomes that describe visible static evidence:

- `authorization_constraint_observed`;
- `external_policy_required`;
- `authorization_constraint_not_observed`;
- `no_supported_object_operation`;
- `incomplete`.

`authorization_constraint_observed` can be supported by an exact query constraint or an exact
owner/tenant comparison. The evidence record identifies which type was observed. It does not claim
the condition dominates every runtime path unless that control-flow property is explicitly in the
supported contract.

`authorization_constraint_not_observed` means a completed bounded path reached a supported object
operation without supported authorization evidence on that path. It remains a review lead with a
`suspected`-level evidence boundary, never a confirmed vulnerability.

### 6.4 Constraint states

Each path records object, principal and tenant constraint state separately:

- `observed`;
- `not_observed`;
- `incomplete`;
- `not_applicable`.

The artifact also records an evidence kind:

- `query_predicate`;
- `post_load_comparison`;
- `external_policy_dependency`;
- `none`.

No single summary boolean may collapse these distinctions.

## 7. Analysis architecture

### 7.1 Required module boundaries

The current `js-ts-route-authorization-audit.mjs` remains the route-level consumer. The old
`js-ts-one-hop-access.mjs` must not grow into an independent recursive analyzer.

The proposed implementation boundaries are:

- `js-ts-selector-evidence.mjs`
  - extracts exact route/action selector origins and local aliases;
- `js-ts-callable-index.mjs`
  - gives every supported function/method a stable internal callable identity;
  - resolves exact imports, exports, re-exports and supported Nest service members;
- `js-ts-function-summary.mjs`
  - summarizes parameter mappings, local aliases, exact calls, returns, supported data operations
    and comparison candidates;
- `js-ts-access-path.mjs`
  - performs deterministic bounded worklist traversal over callable summaries;
  - emits completed and partial path records;
- `js-ts-authorization-evidence.mjs`
  - evaluates supported query predicates and post-load comparisons;
- existing `js-ts-identity-evidence.mjs`
  - remains provider-specific identity evidence;
- existing `js-ts-data-operation-evidence.mjs`
  - remains provider-specific sink evidence and is extended only where v3 constraint semantics
    require it;
- existing `js-ts-module-graph.mjs`
  - remains the only module resolver;
- existing `js-ts-route-authorization-audit.mjs`
  - joins route records to the access-path engine and publishes coverage;
- `js-ts-one-hop-access.mjs`
  - becomes a compatibility facade over the new engine at depth one or is removed only after all
    internal consumers and regressions migrate in one coherent change.

Two production analyzers must not emit overlapping chains for the same entry.

### 7.2 Internal callable identity

An internal callable key contains:

- sanitized project-relative module path;
- declaration kind;
- exported/local symbol identity;
- class identity when applicable;
- member identity when applicable;
- source start location.

The key must not rely on a symbol name alone. Duplicate or ambiguous candidates fail closed.

### 7.3 Flow facts

The engine propagates typed facts rather than arbitrary strings:

```text
object(selector-id, origin, field-name)
principal(identity-provider, identity-origin)
tenant(identity-provider-or-route-origin, field-name)
resource(data-provider, resource-name)
unknown(reason-code)
```

Each fact has an internal origin identity. Public artifacts keep only sanitized category, field
name and source location. Runtime values and source snippets are never retained.

### 7.4 Supported parameter mapping

Stable mapping candidates include:

- identifier argument to identifier parameter;
- a direct alias or supported scalar conversion such as `String(id)`, `Number(id)` or
  `parseInt(id)`;
- exact object literal property to exact object-pattern property;
- exact property access to identifier parameter;
- identifier argument to one unambiguous destructured property;
- assignment-pattern defaults where the mapped value remains exact;
- exact Nest constructor property to exact imported service type.

The following remain partial:

- spread/rest mappings;
- computed properties;
- unknown object mutation before the call;
- arrays used as positional transport;
- multiple candidate aliases for one destructured field;
- overload or interface dispatch without one implementation;
- callback registration where invocation arguments are not statically known.

### 7.5 Supported return mapping

The initial stable return model includes:

- direct return of a supported data operation;
- direct return of an exact local call;
- `await` around either supported return;
- assignment of that exact return to one local identifier;
- one direct single-element array destructuring assignment from that exact return, such as
  `const [record] = rows`; indexing, rest, transforms and ambiguous arrays remain partial;
- direct object-property access on the returned resource for a later comparison;
- one exact object literal return where the tracked field mapping is unambiguous.

Conditional multi-return functions are supported only when every relevant return preserves the same
fact mapping. Otherwise the path is partial with `return_mapping_unresolved`.

### 7.6 Worklist and deduplication

The path engine uses an iterative worklist. Recursion over source-controlled call graphs is not
allowed.

One work item contains:

- entry identity;
- current callable identity;
- ordered call edges;
- object/principal/tenant parameter fact map;
- returned-resource fact when applicable;
- visited callable/fact-state keys;
- accumulated limitation codes.

Deduplication keys include callable identity plus normalized incoming fact categories. A function
reached with an object fact and the same function reached with a principal fact are separate states.

Cycles produce `call_cycle_detected` partial evidence when a relevant fact remains live. They do not
loop, disappear or become `not_applicable`.

### 7.7 Deterministic limits

Initial internal limits are:

- maximum local call edges per path: 4;
- maximum emitted access chains per entry: 50;
- maximum active path states per entry: 512;
- maximum examined call sites per callable summary: 200;
- maximum total access-path state transitions per audit: 50,000;
- existing module, edge, AST-node and source-operation limits remain active.

The exact constants may change during P5 only when a minimized ordinary pattern demonstrates that
the proposed default is insufficient. Every change is recorded in the phase log.

Semantic output must not depend on a wall-clock timeout. Deterministic operation budgets control
analysis. Wall-clock measurements are informational regression evidence only.

Limit exhaustion produces named partial coverage, increments `truncated` or `skipped` as
appropriate and preserves exit code 3 when required evidence is incomplete.

## 8. Authorization-evidence semantics

### 8.1 Object selection

A supported data operation must use a tracked object fact in the operation's object selector. A
constant, unrelated variable or principal-only predicate does not establish that the route-selected
object reached the operation.

### 8.2 Prisma predicates

Supported direct evidence includes exact Prisma `where` shapes for the existing supported object
operations.

- sibling scalar properties in the same object are conjunctive;
- `AND` is conjunctive and may preserve a constraint;
- an `OR` expression counts as a principal/tenant constraint only when every relevant alternative
  constrains the same category;
- `NOT` alone does not establish owner or tenant restriction;
- unresolved spreads, computed keys or helper-produced predicates make constraint evidence
  incomplete;
- a unique object key such as `id` is object selection, not ownership evidence;
- a compound unique key counts only when the principal/tenant component is a tracked matching fact.

### 8.3 Drizzle predicates

Supported direct evidence includes exact existing Drizzle query-builder shapes.

- `and(...)` can establish a principal/tenant constraint;
- `or(...)` establishes it only when every relevant branch contains the constraint;
- `eq(ownerField, principalFact)` and its exact operand reversal are supported;
- string field names or unrelated aliases do not become constraint evidence;
- opaque SQL fragments and unknown helper calls remain incomplete.

### 8.4 Post-load comparisons

The analyzer may record `post_load_comparison` when:

- a supported operation return is assigned to an exact local resource fact;
- one operand is an owner/tenant field on that resource;
- the other operand is a tracked principal/tenant fact;
- the comparison operator is exact equality or inequality;
- the comparison occurs in the same callable or a supported exact returned-resource continuation.

The first stable contract records the comparison. It does not automatically prove denial,
dominance or absence of a bypass. A stricter `denial_branch_observed` subfield may be promoted only
if fixtures distinguish throw/return denial from logging, metrics and dead comparisons.

### 8.5 Authorization helpers and wrappers

Unknown helper names remain candidates. A helper can contribute stable evidence only when the
bounded analyzer resolves its body and observes supported comparison/query evidence inside it.

For route wrappers such as `withAuth(handler)`:

- the exact underlying handler may be analyzed for object/data evidence;
- the route wrapper is recorded as a wrapper edge or route-control candidate;
- authentication/authorization enforcement remains unclassified unless supported structural
  evidence proves the relevant behavior;
- failure to resolve the wrapper never prevents safe inspection of an exact underlying handler, but
  the route-level coverage remains partial where wrapper semantics matter.

## 9. Route-security v3 contract

### 9.1 Version boundary

The v2 schema has `additionalProperties: false` and call edges are capped at two. v0.8.0 therefore
introduces `docs/route-security-v3.schema.json`, keeps the same public file names and records:

- `schemaVersion: 3`;
- analyzer `revision: 3`;
- the existing parser component, version and digest;
- deterministic access-path limits in analyzer metadata;
- selector origin evidence;
- up to four ordered local call edges;
- separate object/principal/tenant constraint states;
- authorization evidence kind and locations;
- one primary incomplete reason plus bounded supporting limitations.

The v1 and v2 schemas remain available for validation of historical artifacts.

### 9.2 Proposed access-chain shape

The final JSON Schema is frozen in P2, but the public model must represent at least:

```json
{
  "status": "completed",
  "outcome": "authorization_constraint_observed",
  "identity": {},
  "objectSelectors": [],
  "callEdges": [],
  "dataOperation": {},
  "authorizationEvidence": [
    {
      "kind": "query_predicate",
      "category": "principal",
      "state": "observed",
      "field": "ownerId",
      "location": { "path": "src/repository.ts", "line": 42 }
    }
  ],
  "reason": null,
  "evidenceBoundary": "..."
}
```

All strings, arrays, paths and locations retain explicit bounds and sanitization. No snippets,
absolute paths or runtime values enter the schema.

### 9.3 Fingerprints

The v3 access-chain fingerprint includes:

- entry identity;
- selector kinds and field names;
- ordered callable edge identities;
- data provider, resource and operation;
- authorization evidence category and kind;
- primary incomplete reason when partial.

Line numbers remain evidence locations and do not become the sole identity. Fingerprints must
distinguish two paths to the same sink and must not merge principal-constrained and unconstrained
paths.

### 9.4 Baseline compatibility

- v1 or v2 route artifacts compared with v3 return
  `not_comparable / route_schema_changed`;
- v3 comparisons require subject, scope, analyzer revision, parser digest and analysis-limit
  compatibility;
- a completed path becoming partial produces `complete_access_path_became_incomplete`;
- observed authorization evidence disappearing produces
  `authorization_evidence_disappeared`;
- a prior object path disappearing under incomplete current framework/path coverage remains
  `unretested`, never fixed or removed;
- a newly completed unconstrained object path is visible as a review regression only under the
  existing explicit opt-in route-regression gate;
- path movement or wrapper changes do not infer developer intent.

## 10. User-facing report contract

### 10.1 Review order

The Markdown report keeps the high-signal queue before the full route inventory:

1. completed object paths with no supported authorization evidence;
2. completed paths that require external policy evidence;
3. partial paths for state-changing or object-addressed entries;
4. routes/actions with no classified scoped control;
5. completed paths with visible authorization evidence;
6. the full route and action inventory.

Visible authorization evidence is still shown because it helps the user understand why a route was
deprioritized and what a later refactor must preserve.

### 10.2 Required explanation fields

Every high-signal entry includes:

- industry term;
- plain-language problem statement;
- selector origin;
- ordered source path in `file:line` form;
- data operation or comparison terminal;
- observed authorization evidence;
- exact missing or unresolved evidence;
- realistic consequence if an authorized retest confirms a defect;
- proposed inspection or fix boundary;
- side-effect risks for sharing, admin, support, background and cross-tenant flows;
- unauthenticated, owner, non-owner and lower-role verification suggestions;
- normal functional retest and rollback criteria.

### 10.3 Example wording

For a completed path without a visible constraint:

> Industry term: possible Broken Object Level Authorization review lead. Plain language: a value
> selected by the request reaches a database lookup for one record, and this bounded source path did
> not show a condition tying the record to the current user or tenant. This does not prove another
> user can access it. Review the listed path and run an authorized owner/non-owner test before
> changing code.

For a partial path:

> The request-selected ID reached `ProjectService.find`, but the next call target was dynamic and
> could not be resolved. No conclusion is available for the repository query. Treat the remaining
> path as unreviewed.

For an observed constraint:

> The selected record ID and current user's ID both reach the supported query, where `ownerId` is
> compared with the principal value. This is useful static evidence, but it does not prove the
> deployed route always executes this query or denies every alternate path.

## 11. Evaluation and ground-truth design

### 11.1 Historical ledger freeze

Before production implementation, P1 creates a v0.8.0 evaluation ledger from the current 32-entry
v0.7.0 manual review. Each entry records:

- project, immutable commit, route/action and source location;
- manual assessment from the historical review;
- selector origin expected under v0.8.0;
- expected callable path and edge count, where manually established;
- expected data provider and operation, where manually established;
- expected authorization evidence category;
- `eligibleForV080` with a reason decided before implementation;
- expected status: completed, partial or not applicable;
- whether the sample is ordinary, intentionally vulnerable or a known fixed-vulnerability pair;
- reviewer notes and evidence links.

Historical statements remain historical. The new ledger does not rewrite the v0.7.0 artifact or
pretend the original tool produced v0.8.0 evidence.

### 11.2 Project cap

The evaluation uses at most five fixed public project commits:

- retain the existing NestJS Boilerplate, Vercel Chatbot and Formbricks commits for longitudinal
  comparison;
- retain Documenso only for expected-public negative behavior if it contributes useful stable
  cases;
- add at most one intentionally vulnerable or known-vulnerability JavaScript/TypeScript project
  after license, fixed commit and ground-truth suitability are recorded;
- do not add projects merely to improve aggregate counts.

Project dependencies and applications are not executed for this source review. Any later active
verification is a separate authorized activity and is outside the v0.8.0 release gate.

### 11.3 Metrics and anti-metrics

The review publishes:

- total manually labeled entries;
- structurally eligible v0.8.0 paths;
- completed, partial, not-applicable and excluded paths;
- primary partial reason distribution;
- selector-origin distribution;
- path-depth distribution;
- data-provider distribution;
- authorization-evidence-kind distribution;
- unexpected completed paths;
- expected completed paths missed;
- changes from the frozen v0.7.0 observations.

Release targets are:

- at least 70% of the frozen structurally eligible real paths are completed;
- at least six completed real paths across at least two projects;
- both Prisma and Drizzle contribute completed ordinary-project evidence unless one remains
  explicitly experimental with a recorded cause;
- at least one query-constraint and one post-load-comparison case are represented;
- zero unexpected `completed` results in labeled ambiguous or unsupported cases;
- every miss remains visible with a named reason;
- no production precision, recall, reachability or exploitability percentage is published.

The 70% denominator is frozen in P1. Cases may move out of the denominator only when a source or
labeling error is documented before the relevant implementation phase; they cannot be removed
because the analyzer failed to support them.

Fixture conformance, path completion and production vulnerability accuracy remain separate
concepts. `TP`, `FP` and `FN` labels are used only for a corpus with independently grounded
vulnerability truth.

### 11.4 Real-world regressions

At least the following defect classes become named minimized regressions:

- query-selected ID omitted from an otherwise visible Auth.js ownership path;
- JSON-body-selected ID omitted from an otherwise visible path;
- second exact local edge stopped before a supported repository operation;
- exact local re-export prevented callable resolution;
- wrapper hid an analyzable underlying handler;
- an ambiguous wrapper or dynamic call incorrectly became completed;
- `OR` query semantics incorrectly treated one constrained branch as globally constrained;
- a post-load comparison was either missed or overclaimed as enforced denial;
- budget exhaustion incorrectly produced completed coverage.

Each regression records the observed failure, protected contract, minimized fixture, test command
and plant-the-failure result.

## 14. Release stop conditions

Stop implementation, retain partial behavior or keep a family experimental when:

- a call target can be selected only by symbol/member name;
- a local import, re-export, wrapper or service has more than one possible target;
- value propagation requires spread/rest, computed mutation or runtime dispatch;
- a cycle or operation limit would be hidden from coverage;
- a user-supplied `userId` can be confused with authenticated identity;
- one constrained `OR` branch would make the whole operation look constrained;
- a post-load comparison would be described as enforced denial without supported control-flow
  evidence;
- a missing visible constraint would become confirmed BOLA/IDOR;
- an unresolved RLS or external policy would be displayed as absent protection;
- a v2 baseline could appear comparable under v3 semantics;
- an access path is completed after any relevant parser/module/path evidence failed;
- the frozen review contains any unexpected completed ambiguous/unsupported case;
- the frozen eligible completion target falls below 70%;
- fewer than six grounded completed paths remain after honest exclusions;
- median ordinary-review runtime exceeds 2x without understood cause or explicit owner acceptance;
- required runtime files diverge between npm, Skill, CLI and Action channels;
- validation grows beyond the bounded plan without a concrete defect or contract requiring it.

The appropriate response to a stop condition is to narrow the stable boundary, keep the behavior
experimental or defer it. Weakening evidence states or changing the denominator is not an accepted
response.

## 15. Risk register

| Risk | User impact | Control | Stop/escalation signal |
|---|---|---|---|
| Path explosion | slow or incomplete audit | summaries, worklist dedupe and deterministic limits | state/global budget reached on ordinary corpus |
| False completed path | misplaced trust | exact single-target resolution and fail-closed ambiguity | any labeled ambiguous case completes |
| Principal/object fact confusion | unsafe ownership conclusion | typed facts and origin identities | body `userId` becomes authenticated principal |
| Query boolean overclaim | unsafe constrained outcome | explicit AND/OR/NOT semantics | partially constrained OR is observed |
| Wrapper overclaim | wrapper name presented as control | separate handler inspection from enforcement | wrapper name alone changes auth state |
| Comparison overclaim | logging/comparison presented as denial | evidence-kind separation and benign neighbors | unrelated comparison affects outcome |
| Baseline churn | noisy or false regressions | v3 boundary and semantic fingerprints | v2/v3 comparison appears compatible |
| Output data leak | source/user data in report | metadata-only facts and bounded sanitization | snippet, absolute path or runtime value persists |
| Corpus gaming | misleading completion metric | denominator freeze and digest-bound ledger | post-implementation eligibility changes |
| Architecture duplication | inconsistent chains | one path engine and one route consumer | duplicate chain emitters remain in production |
| Framework scope creep | delayed unstable release | no new framework/ORM rule | unrelated framework required for target metric |
| Release-process dominance | product work displaced | one final full gate and minimal consumers | duplicate unchanged-tree evidence work appears |
